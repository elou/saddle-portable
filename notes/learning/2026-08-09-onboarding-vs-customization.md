# Onboarding is not the customization ceiling

## 2026-08-09 — Separate public setup from ongoing personalization

Context:
The release handoff assumed a named destination computer and recommended transferring only two personal-context sections. Emily clarified that Saddle is publicly downloadable by anyone and that a narrow starter scope may suit onboarding but not customization.

Learning:
Distribution, onboarding, and customization are three different jobs. Distribution installs Saddle on any computer. Onboarding gets a useful neutral profile running with few decisions. Customization is an ongoing profile workbench and must allow broad user-authored personal context, operating preferences, standards, and capabilities. Integration authoring remains outside version 0.1 until a credential-free portable declaration contract exists.

Risk:
If privacy-safe onboarding defaults become permanent product limits, Terra will feel generic and users will mistake consent controls for missing customization. A device-specific handoff model also makes a public npm/GitHub package look like a private sync utility.

Follow-up:
Remove named-destination assumptions. Keep personal items off by default during onboarding, but make every supported category available. Add a separate, source-preserving customization path with exact preview, item-level consent at export/install, no-overwrite publication, and interrupted-publication recovery. Treat consent as control over disclosure, not a limit on the profile's expressive range.
