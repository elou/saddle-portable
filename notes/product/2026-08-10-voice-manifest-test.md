# Voice manifest used for the fresh setup script

- Use concise, plain English throughout.
- Name the person's job before the system's label.
- Do not lead with internal words such as profile, manifest, source, destination, projection, digest, module, runtime, or commit. When a technical term is necessary because it appears in the current UI, explain it in the same sentence using ordinary words.
- Plainness never changes with depth. Add detail only when it helps Emily understand a choice, a consequence, or what the product does.
- Use the concrete nouns already in the product: this computer, another computer, Claude, Codex, folder, file, instructions, setup.
- Prefer short sentences. Avoid doc-speak, abstract category labels, explanatory colons, and procedural narration.
- For every screen, make these answers easy to find: What am I doing? What happens when I continue? What can I change later? What will not happen automatically?
- Describe buttons literally. If a button only moves forward, say that. If it reads or writes files, say that.
- Separate user-facing meaning from optional technical evidence. Do not front-load hashes, paths, ids, or implementation terms.
- Do not praise, flatter, anthropomorphize the assistant, or add throat-clearing.
- Do not invent an editing taxonomy. The document itself should be straightforward to edit.
